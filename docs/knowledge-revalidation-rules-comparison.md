# 知识卡分类核验规则对比

更新日期：2026-11-27

本文档区分两套规则：

- **方案 A：当前已实施规则**，对应 FinLens 0.2.10 的代码。
- **方案 B：新规则**，用于修正“来源真实相关但独立票仍为 0”和“模型失败被显示成证据不足”的问题；FinLens 0.3.0 已实施。

两套规则共享分类本体，但在独立分析、检索计票、冲突处理和自动应用条件上不同。

## 一、共享的分类本体

### 1. 三个分类维度

`category` 表示知识本体，只能有一个主分类：

- `finance`：金融资产、合约、机构、融资、估值、保险、投资、市场定价或金融风险。
- `background`：政治、法律、监管、产业、技术、社会、治理、科研或实体经营背景。
- `method`：具有目的、假设、输入、变换步骤、输出解释和适用边界的可重复分析程序。

`cardType` 表示解释形式：

- `concept`：定义、指标、制度、工具或角色。
- `phenomenon`：可观察事件、趋势或结果。
- `mechanism`：因果链、传导路径或制度运行逻辑。
- `method`：可执行、可重复的分析程序。

`categories` 表示板块归属：

- 最多两个。
- 第一个是主分类。
- 第二个是独立且实质成立的交叉分类。
- `cardType=mechanism` 不自动等于 `category=method`。

### 2. 主解释对象

分类首先判断卡片主要在解释什么对象，不根据文章主题、媒体类型、案例字段或模型初始标签直接分类。

核心顺序：

1. 是否存在完整、可迁移的方法程序。
2. 主对象是否属于金融本体。
3. 背景对象是否同时存在独立、实质的金融关系。
4. 都不满足时归 `background`。

金融估值是特殊情形：主分类为 `finance`，具备完整计算程序时交叉 `method`。

### 3. 正文和案例的边界

- `one` 和 `body` 用于判断主解释对象，也用于检查卡片正文是否与术语一致。
- `cases` 不参与分类。
- 正文与术语错配可以阻止自动应用，但不应替代独立分类。
- 模型初始分类只是弱提示，不是分类证据。

## 二、方案 A：当前已实施规则

### 1. 规则候选

服务端先用本地规则 `classifyKnowledgeCategory(card)` 生成候选分类。

候选来自：

- 明确术语规则；
- 金融本体关键词；
- 背景边界关键词；
- 方法程序证据；
- 默认背景回退。

当前仍将以下对象作为分类输入：

- `term`
- `en`
- `cardType`
- `one`
- `body`
- `classificationReason`
- `categoryReason`
- `methodSteps`
- `scenarios`
- `related`
- `match`

案例字段不参与分类。

### 2. 卡片一致性证据

从 `one` 和 `body` 中切分句子，形成：

- **主对象证据**：术语定义、本体、机制或关系。
- **独立交叉证据**：支持第二分类的独立正文片段。
- **明确否定证据**：包含“不涉及、不包含、没有、并非、而不是”等表述的片段。

卡片一致性证据的判断条件：

- 至少有一个主对象片段；
- 主对象片段有实质内容，不能只是术语本身；
- 正文总长度不少于 12 个字符；
- 若候选包含交叉分类，必须有独立交叉片段。

该层结论写入 `evidence.sufficient`。

注意：`evidence.sufficient` 表示“卡片正文与规则候选是否一致”，不是独立分类证据。

### 3. 联网检索

当 `online=true` 时：

1. 使用术语英文名或中文名搜索新闻与论文。
2. 新闻优先使用 Tavily；无结果时使用 GDELT。
3. 论文使用 Crossref。
4. 每类检索使用约 8 秒超时。
5. 检索结果缓存约 6 小时。
6. 只保留被标记为 `verified` 的来源。
7. 最多取前 6 条送入独立模型分析。

当前来源文本构造规则：

- 保留标题；
- GDELT 的“相关市场报道，来源国”说明会被删除；
- Crossref 的通用元数据说明会被删除；
- 最终多数来源只剩标题。

### 4. 独立模型分析

若存在 API Key、本地凭据或 CC Switch 供应商：

- 模型只接收术语和检索摘要；
- 模型不得使用卡片正文；
- 模型返回 `category`、`categories`、`confidence`、`reason`、`evidenceSourceIndexes`；
- 模型调用失败时被捕获并返回 `null`；
- UI 不会单独显示模型失败原因。

当前模型分析结果写入：

- `evidence.model`
- `evidence.modelCategory`
- `evidence.modelConfidence`

`evidenceSourceIndexes` 虽然后返回，但没有参与最终计票。

### 5. 独立计票

当前计票公式：

```text
模型票 = 模型主分类属于规则候选 categories
      或模型理由命中分类关键词

检索票 = 去重后的来源中，
      标题或非通用描述命中规则候选分类关键词的数量

独立票数 = 模型票 + 检索票
独立证据充分 = 独立票数 >= 2
```

分类关键词由固定正则维护，例如：

- finance：equity、security、valuation、cash flow、debt、financing、credit、liquidity、interest rate、currency、insurance、portfolio、investment、return、yield、spread、tax；
- background：law、legal、regulation、policy、court、institution、governance、trust、political、industry、technology、research、science；
- method：analysis、method、model、framework、estimate、forecast、assumption、scenario、simulation、validation、procedure、calculation。

当前规则的要求：

- 来源目录不算票；
- 未验证来源不算票；
- 同一 URL 只算一次；
- 模型票最多 1 票；
- 检索票按命中的独立来源数量累加；
- 至少 2 票才允许提出分类变更。

### 6. 当前自动变更条件

规则候选与当前分类不同时，才形成潜在变更。

自动建议变更需要：

```text
分类有差异
且独立证据充分
且没有正文一致性警告
```

UI 默认只勾选：

```text
recommendation = change
changed = true
independentSufficient = true
无正文警告
categoryConfidence >= 0.85
```

真正应用时再次要求：

```text
用户已勾选
changed = true
independentSufficient = true
```

### 7. 当前置信度

若独立证据充分：

```text
置信度 = max(规则置信度, 0.78) + min(0.08, 独立票数 * 0.025)
若卡片正文一致性充分，再增加 0.02
```

若独立证据不足：

```text
置信度 = min(规则置信度, 0.70)
若卡片正文一致性不足，再降到不超过 0.55
若规则建议变更但独立证据不足，再降到不超过 0.60
```

否定证据和正文警告会继续扣分。

独立证据不足时：

- `categoryConfidence = null`；
- UI 显示“无置信度”；
- 卡片不自动勾选。

### 8. 当前推荐状态

- 规则分类未变化且无警告：`keep`
- 规则分类未变化但有警告：`review`
- 规则分类变化但独立证据不足：`review`
- 规则分类变化、独立证据充分但有警告：`review`
- 规则分类变化、独立证据充分且无警告：`change`

### 9. 当前状态显示

只要 `independentSufficient !== true`，UI 就显示：

```text
独立证据不足
```

即使：

- 规则候选与当前分类一致；
- 模型已经明确支持分类；
- 检索返回了真实相关来源；
- 实际原因是标题关键词没有命中；
- 实际原因是模型请求失败；
- 实际原因是某一路检索超时。

### 10. 当前规则的主要问题

1. 来源相关性由固定关键词决定，而不是由独立模型实际引用决定。
2. 模型已经返回 `evidenceSourceIndexes`，当前计票却没有使用。
3. GDELT 和 Crossref 的有用描述被删除，只剩标题参与判断。
4. `labour`、`wage`、`funding`、`payment`、`futures` 等实际语义没有完整进入关键词表。
5. 模型请求失败后静默变成空结果，UI 只显示“独立证据不足”。
6. 模型主分类必须属于规则候选分类，模型并未真正独立挑战规则。
7. 部分检索来源成功、另一路超时，也能产生 `online=verified` 和 `onlineError` 并存的状态，但 UI 不区分。
8. 真实的官方来源可能因为没有命中分类词而不计票。

## 三、方案 B：新提议规则

### 1. 基本原则

- 本地规则只生成候选，不是证据。
- 每张卡都必须执行独立模型分析和来源核验，才能判断是否需要变更。
- 不因为“看起来未变更”而跳过核验。
- 卡片正文只做一致性检查，不参与独立分类计票。
- 至少两条不同的真实外部来源支持，才允许自动提出分类变更。
- 模型不直接充当来源票；模型负责分类和选择来源，来源票来自真实检索结果。

### 2. 独立模型输出

模型必须返回结构化结果：

```json
{
  "category": "finance",
  "categories": ["finance", "background"],
  "confidence": 0.91,
  "reason": "说明主解释对象与交叉依据",
  "sourceSupport": [
    {
      "index": 1,
      "quote": "来源中支持分类的标题、摘要或短句",
      "supports": ["finance"],
      "strength": "direct"
    }
  ],
  "limitations": "说明来源不足、冲突或歧义"
}
```

约束：

- 只能引用本次实际提供的来源序号；
- 不能引用卡片正文；
- 不能编造 URL、标题、作者或摘要；
- `quote` 必须能在对应来源的标题、描述或元数据中找到；
- 每个来源只能支持一个主分类和最多一个交叉分类；
- 模型必须明确区分 `direct`、`contextual` 和 `insufficient`。

### 3. 来源票规则

一条来源票必须同时满足：

1. 来源来自本次实际检索结果；
2. 来源 URL 有效；
3. 来源为专业或官方来源；
4. 来源通过实际 HTTP 检索获得；
5. 模型明确引用了该来源序号；
6. 模型给出可核对的短引文或支持说明；
7. 引文与目标分类一致；
8. URL 未被用于同一分类的重复计票。

不计票：

- 来源目录；
- 未验证来源；
- 模型自行生成的 URL；
- 无效来源序号；
- 只有泛化说明、无法核对内容的来源；
- 重复 URL；
- 与目标分类无关的来源；
- 卡片的 `one`、`body`、`cases`。

### 4. 独立分类结论

来源核验后得到：

- `ruleCandidate`：本地规则候选；
- `modelConclusion`：独立模型分类；
- `validSourceVotes`：经过验证的来源票；
- `modelConflict`：模型与规则是否存在主分类冲突。

新规则要求：

```text
模型给出明确主分类
且至少两条有效来源支持该分类
```

才进入分类是否变更的决策。

模型本身不计入“两条来源票”。模型是分析器，来源是证据。

### 5. 分类决策

#### 情况一：来源不足

若有效来源少于 2 条：

- 不自动变更；
- 显示“外部来源不足”；
- 展示模型分类、来源票数和失败原因；
- 不显示固定 `50%`；
- `categoryConfidence = null`。

#### 情况二：模型与规则一致

若模型主分类与规则候选一致，且有至少两条来源：

- 当前分类与规则一致：显示“分类已确认”；
- 当前分类与规则不同：生成“建议变更”；
- 若正文有警告，仍进入人工确认；
- 应用前仍要求用户手动勾选并确认。

#### 情况三：模型与规则冲突

若模型主分类与规则候选不同：

- 不自动应用规则候选；
- 显示“规则与模型冲突”；
- 同时展示两边的分类、理由和来源；
- 进入人工确认；
- 不允许用单边关键词覆盖模型或规则。

#### 情况四：模型失败

若模型请求超时、凭据失败、输出无效或无法解析：

- 显示“模型核验失败”；
- 不把失败伪装成“证据不足”；
- 不自动应用任何分类修改；
- 保留可重试入口。

#### 情况五：检索部分失败

若新闻检索失败但论文检索成功，或相反：

- 保留成功来源；
- 显示“部分检索失败”；
- 成功来源满 2 条并满足引文要求时仍可形成结论；
- 来源不足时才进入“外部来源不足”。

### 6. 正文一致性

正文一致性仍独立判断：

- 主对象片段是否有实质内容；
- 交叉分类是否有独立片段；
- 是否存在明确否定片段；
- 术语与正文是否明显错配。

正文一致性不决定独立分类，只决定：

- 是否阻止自动应用；
- 是否显示内容修改确认窗口；
- 是否需要同时修改正文或案例。

### 7. 置信度

只有来源票达到要求后才显示数值置信度。

建议区间：

- 两条直接来源且模型一致：`0.85-0.94`
- 三条以上直接来源且模型一致：`0.95-0.99`
- 来源为背景性、间接性或存在轻微冲突：`0.75-0.84`
- 来源不足、模型失败、规则冲突：无数值置信度

置信度不得用固定 `50%` 表示核验失败。

### 8. 自动勾选与应用

默认自动勾选仍只针对高确定性变更：

```text
分类确实不同
模型与规则一致
至少两条有效外部来源
正文无明显错配
无未解决冲突
置信度 >= 0.85
```

应用时再次校验相同条件。

以下情况不自动勾选：

- 来源不足；
- 模型失败；
- 模型与规则冲突；
- 正文错配；
- 来源引文不可核对；
- 只有来源目录；
- 只有一条来源；
- 置信度不足。

### 9. UI 状态

至少区分：

- `分类已确认`
- `建议变更`
- `外部来源不足`
- `规则与模型冲突`
- `模型核验失败`
- `部分检索失败`
- `正文与术语错配`
- `等待人工确认`

不能再用一个“独立证据不足”覆盖全部失败类型。

### 10. 可追溯记录

每条核验结果应保存：

- 规则候选分类与理由；
- 模型分类、分类组、置信度与理由；
- 模型引用的来源序号与短引文；
- 实际检索来源标题、发布者、URL、状态；
- 有效来源票数；
- 无效来源及原因；
- 模型失败或检索失败原因；
- 最终状态和是否允许自动应用。

## 四、完整对比

| 项目 | 方案 A：当前已实施 | 方案 B：新提议 |
|---|---|---|
| 规则候选用途 | 作为核验目标和模型支持对象 | 只作为候选，不直接计票 |
| 卡片正文 | 做一致性检查 | 仍只做一致性检查 |
| 每张卡是否分析 | 联网时理论上都分析，但失败会静默 | 必须分析后才能判断是否变更 |
| 模型作用 |  corroborate 规则候选 | 独立给出分类、理由、来源引用和限制 |
| 模型失败 | 返回 `null`，UI 显示证据不足 | 明确显示“模型核验失败” |
| 检索计票 | 标题/描述命中固定关键词 | 模型实际引用且验证通过的真实来源 |
| `evidenceSourceIndexes` | 返回但不使用 | 作为核心计票依据 |
| 来源描述 | GDELT/Crossref 通用描述被删除 | 保留并允许引文核对 |
| 两票含义 | 模型 1 票 + 命中关键词的来源票 | 至少 2 条独立外部来源票 |
| 规则与模型冲突 | 模型票可能直接丢失 | 显示冲突，进入人工确认 |
| 来源不足 | 显示“独立证据不足” | 显示“外部来源不足” |
| 检索部分失败 | `onlineError` 有值但状态仍可能 verified | 单独显示部分失败，成功来源保留 |
| 未变更卡 | 仍可能显示独立证据不足 | 仍需分析，但显示“分类已确认” |
| 数值置信度 | 不足时仍可能由回退逻辑产生低于 0.7 的值，但最终为 null | 来源达标才显示 |
| 固定 50% | 不使用，但失败状态可能被误读 | 明确禁止表示核验失败 |
| 自动变更 | 规则差异 + 模型/关键词合计 >= 2 票 | 模型与规则一致 + 至少 2 条有效来源 |
| 模型偏见 | 只允许支持规则候选，无法独立纠错 | 可独立提出分类；冲突时人工处理 |
| 来源目录 | 不计票 | 继续不计票 |
| 案例字段 | 不参与分类 | 继续不参与分类 |
| 可解释性 | 计票原因弱，难看出为何不足 | 每个来源和失败原因可追溯 |
| 误杀风险 | 高，相关标题不命中词表即 0 票 | 低，由模型引用和来源验证决定 |
| 误放行风险 | 关键词命中可能误计票 | 需要模型明确引用和有效 URL，更严格 |

## 五、已复现案例对照

### `co-financing`

方案 A：

- 模型支持 finance；
- 来源标题含 `financing`；
- 获得模型 1 票 + 检索 4 票；
- 结果充分。

方案 B：

- 模型给出 finance；
- 至少两条来源被模型逐条引用；
- 来源 URL 和短引文可核对；
- 结果充分。

### `tight labour markets and wage growth`

方案 A：

- 模型支持 background；
- 检索到劳工市场、工资增长、全球工资报告等 4 条来源；
- 标题不含背景关键词表中的固定词；
- 检索票为 0；
- 只有模型 1 票，结果不足。

方案 B：

- 模型引用劳工市场与工资增长来源；
- 每条来源提供标题或摘要短引文；
- 两条以上来源通过 URL 和引文校验；
- 结果充分，显示“分类已确认”或“建议变更”。

### `Funding payments`

方案 A：

- 模型支持 finance；
- 检索到永续合约和资金支付相关来源；
- `funding`、`payment`、`futures` 未完整进入金融关键词表；
- 检索票为 0；
- 只有模型 1 票，结果不足。

方案 B：

- 模型引用永续合约和 funding payment 相关来源；
- 有效 URL 去重；
- 两条来源可核对；
- 形成充分来源票。

### 模型超时

方案 A：

- 模型异常被捕获为 `null`；
- 检索票不足时显示“独立证据不足”；
- 用户无法区分模型失败和真实证据不足。

方案 B：

- 显示“模型核验失败”；
- 展示失败类型和重试入口；
- 不生成分类变更；
- 不显示伪置信度。

## 六、新规则实施后的测试要求

1. 模型只能引用真实存在的来源序号。
2. 无效序号、重复 URL、来源目录不能计票。
3. 标题没有分类关键词、但被模型引用且短引文有效的来源可以计票。
4. 至少两条来源票才能自动变更。
5. 模型失败与来源不足显示不同状态。
6. 规则与模型冲突必须进入人工确认。
7. 正文错配不改变独立分类，但阻止自动应用。
8. 未变更卡也执行独立分析，确认后显示“分类已确认”。
9. 部分检索失败但成功来源足够时仍可形成结论。
10. 置信度只由已核验来源和模型结论生成，不使用固定 50%。

## 七、结论

方案 A 的核心问题不是“模型不够用”，而是：

- 规则关键词把真实相关来源误杀；
- 模型已经选择的来源没有参与计票；
- 模型失败和来源不足被混成同一个状态；
- 模型被迫支持规则候选，失去独立纠错能力。

方案 B 把“规则、模型、真实来源、正文一致性”拆成四个独立层，并要求至少两条真实来源支持后才能自动变更。这样才符合“独立核验”的本意。
